# 24：显式开启 Git 远端发布

**状态：** 已完成（2026-03-10）。

**交付结果：** 管理员开启远端操作后，用户将已批准发布关联到指定远端和 tag。

**前置依赖：** 23 生成可核验的正式交付包。

**验收条件：**

- [x] pull、push 默认关闭；管理员显式启用并限定 remote 后，发布面板显示目标、批准绑定的 source revision 与 tag。操作只创建/推送该 revision 的 tag，不 commit、不 pull，暂存区内容保持不变。
- [x] 远端不允许、manifest 无效、tag 冲突、无权限或断网均报告“远端未完成”，并明确本地正式包仍然完整；推送不读取或上传包内凭据、缓存和构建产物。
- [x] 真实 bare Git 远端验证首次发布及幂等重试；预置冲突 tag 后操作失败且远端引用仍指向原 commit，不 force、不自动处理冲突。
- [x] 桌面生产构建和远端发布测试通过。

**范围限制：** 不把 Git 推送成功等同于交付包上传成功。

**开发方式：** 先核对已有实现与未合并修改；沿上述用户行为打通所需状态、真实执行、界面和测试。必要整理先做且保持原行为；不要另拆为纯前端或纯后端票。若一个独立上下文无法完成，按可演示行为继续拆分。

**演示：** 从用户入口执行“交付结果”，展示成功成果、一个相关失败及恢复；以验收中的实际数据核对结果。

**真实操作证据：** 测试创建两个真实 Git 仓库，将正式包 manifest 绑定的 commit 发布为 `reify/candidate`，从 bare remote 反查 tag 与 commit 一致；保留的 staged 文件在发布前后 `git status --porcelain` 完全相同。再次发布返回 reused。另一个远端 tag 预先绑定旧 commit 后被拒绝，远端 tag 未被覆盖，本地 release manifest 仍可读取。结果对象固定返回 `packageUploaded: false`，避免把 Git tag 发布误报成正式包上传。
