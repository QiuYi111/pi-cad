# Reify 产品整改计划

状态：执行稿  
范围：桌面端、Agent 运行时、工作流、审批、版本管理、安装与真实任务测试

## 1. 目标

Reify 应让工程师从一句需求开始，完成设计、检查、修改、批准和交付，同时始终看清：

- 当前在做什么；
- 正在查看哪个项目、对话和模型；
- Agent 为什么停下、失败或请求确认；
- 哪个版本可以继续修改或交付；
- 哪些决定来自机器审查，哪些来自人。

本轮不建设不可变 STEP 仓库，也不建设逐条“需求—检查”数据库。源码与流程版本交给 Git；STEP、渲染和仿真结果继续作为工作流产物，以哈希绑定当前提交。

## 2. 产品原则

1. Agent 负责推理，Python 负责组合，确定性程序负责构建和测量。
2. 工作流只表达任务等级、允许操作、必要交付和审批，不替 Agent 设计。
3. 少量完整操作优于大量细碎调用；底层通用接口继续保留。
4. 远端 Git、发布和人工批准必须显式开启，不能靠提示词假装完成。
5. 主界面服务当前工程决定；工作流编辑和轨迹分析属于高级工具。
6. 每项新增复杂度必须通过真实任务证明价值。

## 3. 整改范围

### A. Python 组合宏

保留现有可编程接口，增加少量便利宏：

- `save_and_check(...)`：构建、基础检查、七视图和工作流记录；
- `submit_current(...)`：整理当前候选并提交机器审查；
- `publish_current(...)`：检查批准状态、执行 Git 发布并生成交付摘要；
- `restore_source(...)`：切换到指定 Git 版本并重新构建。

宏不能绕过 `authorize()`，也不增加第二套状态机。`workflow.current()` 和状态卡只提示“可以组合操作”，不要求 Agent 背诵固定调用仪式。

验收：宏与手动 Python 组合产生相同的授权、记录和错误；任一步失败都返回可恢复状态。

### B. 分级工作流

新增少量独立工作流，不在一个工作流里堆条件：

| 工作流 | 用途 | 默认审查 |
| --- | --- | --- |
| `mechanical.quick-check` | 查看 STEP、测量、基础判断 | 无 |
| `mechanical.quick-build` | 明确的小型单零件 | 可选机器审查 |
| `mechanical.controlled-change` | 修改已有设计并比较 | 机器审查 |
| `mechanical.one-shot` | 新设计或装配体 | 机器审查 |
| `mechanical.release` | 正式交付 | 机器审查 + 人工批准 |

工作流继续支持阶段 Git 钩子。概念图只在需要概念探索的工作流中成为义务。

验收：同一简单任务在轻量工作流中减少无关阶段；正式发布仍不能跳过批准。

### C. 人工批准

新增独立的批准对象，与机器 Reviewer 和用户评分分开：

```text
approvalId
projectId
workflowId + workflowHash
sourceRevision
artifactHash
approver
scope
decision
comment
createdAt
revokedAt
```

桌面端提供“批准此版本”“要求修改”“撤销批准”。发布操作必须检查当前 Git SHA、产物哈希和批准记录一致。批准后源码或候选变化，旧批准立即显示为过期。

验收：没有批准的正式发布被拒绝；批准人、版本、范围和时间可追溯；撤销后不能继续发布。

### D. Git 版本治理

继续完善已加入的工作流 Git 策略：

- 初始化项目仓库并建立源码基线；
- 阶段进入或完成时执行配置的 `commit`；
- `pull`、`push` 默认关闭；
- 忽略 STEP、图片、缓存和敏感文件；
- 已有暂存内容时拒绝自动提交；
- 工作流提交绑定 Git SHA；
- 支持选择工作流、Skill 和执行代码的已批准 tag；
- 支持升级、回退和固定版本。

蒸馏只生成候选修改。候选必须通过失败节点回放、保留任务回归和人工批准，才能合并到正式分支或发布 tag。

验收：升级可复现、失败可回退；旧任务仍使用启动时固定的规则；Git 冲突不会被自动覆盖。

### E. UI/UX 重塑

#### E1. 视觉语言

品牌基础沿用 Reify · 器成：

- Obsidian `#0E0E0E`：主工作区；
- Graphite `#646464`：次级信息；
- Stone `#E8E6E1`：亮色背景和高亮表面；
- Sage `#5B6F63`：可信、可继续；
- Champagne `#C9B89F`：人工决定与发布。

字体分工：产品标题使用克制的现代无衬线；正文强调中文可读性；尺寸、哈希、坐标和日志使用等宽字体。图标统一使用描摹后的器成标志和线性工程图标，不混用装饰性符号。

布局不复制通用聊天软件。CAD 模型是主角，聊天是操作通道。品牌记忆点是一条贯穿顶部的“版本轨迹线”：它同时表达阶段、Git 版本、机器审查和人工批准，不做纯装饰。

动画只用于四件事：状态推进、模型替换、检查定位、批准落章。支持减少动画；持续计算不能播放无意义循环动画。

#### E2. 使用体验

主工作台固定回答六个问题：当前任务、当前模型、本次变化、检查结果、阻塞原因、可交付版本。

```text
┌ 项目 / 对话 ─── 版本轨迹 ─── 当前权限 / 模型 ┐
├──────────────┬──────────────────────────────┤
│ 对话与事件流   │                              │
│              │          CAD 主视图           │
│ 工具图片/结果  │                              │
│              ├──────────────────────────────┤
│ 输入框        │ 参数 / 检查 / 版本 / 批准抽屉 │
└──────────────┴──────────────────────────────┘
```

重点整改：

- 项目、对话和 Viewer 状态严格绑定，切换时一起恢复；
- 对话支持新建、自动命名、恢复和运行中切换；
- Thinking、流式文本、工具执行、等待和失败使用不同状态；
- Build、Probe、Simulation 返回的图片和模型直接可见；
- 多零件可选择、隐藏、隔离、比较，保持零件身份；
- 参数面板显示来源、单位、合法范围、预览与应用差异；
- 机器审查展示实际发现和证据；人工批准单独呈现；
- 错误必须说明发生了什么、数据是否保留、下一步能做什么；
- Workflow、Trajectories 降为管理页，主工作台不暴露内部手续。

验收：在 1366×768、1920×1080 和高缩放屏幕可用；键盘可达；切换页面不丢会话；模型更新后 Viewer 自动刷新；中止后可继续输入。

### F. 真实端到端测试

建立正式测试矩阵：

1. Windows + WSL 全新安装、已有 Ubuntu、缺少可选组件；
2. macOS 原生安装；
3. Linux 原生安装；
4. OAuth 登录、过期、取消和网络失败；
5. 新建项目、打开项目、切换项目和恢复对话；
6. 快速检查、简单建模、受控修改、装配设计、仿真和正式发布；
7. 中止、重启、构建超时、Reviewer 失败、Git 冲突和远端无权限；
8. 参数修改、多零件选择、版本比较、人工批准与撤销；
9. 蒸馏候选的失败节点回放和保留任务回归。

测试必须使用真实 Prime、真实 sidecar、真实 Python 内核和真实 Viewer。演示运行时只用于视觉快照，不能作为功能通过依据。

验收记录至少包含：成功状态、耗时、首个可见反馈时间、模型与 Token、工具错误、恢复结果、Git SHA、产物哈希和截图。

## 4. 实施阶段

### M0：收口当前基础

- 合并现有 UI、缓存、取消、项目切换、PNG 校验和 Git 修复；
- 补装配零件身份回归测试；
- 建立一组固定真实任务。

完成标准：主分支干净；单元、桌面和安装测试通过；旧问题均有回归测试。

### M1：宏与分级工作流

- 实现四个 Python 宏；
- 加入轻量检查、轻量建模和正式发布工作流；
- 更新状态卡与用户文档。

完成标准：简单任务不再经过无关阶段；正式任务保持审查与发布约束。

### M2：批准与 Git 发布

- 实现批准、撤销和过期；
- 增加 Git tag、固定版本、升级和回退；
- 蒸馏改为候选分支发布流程。

完成标准：正式发布同时绑定源码、产物和批准；规则更新可回退。

### M3：工作台重塑

- 建立视觉变量、字体、图标和动效规范；
- 重构主工作台信息结构；
- 完成版本轨迹、检查、参数和批准抽屉；
- 完成会话、Viewer 和项目同步。

完成标准：真实任务全程无需打开内部日志；工程师能判断当前版本是否可交付。

### M4：真实 E2E 与发布

- 执行三平台测试矩阵；
- 修复安装、恢复、性能和错误提示；
- 记录基线并建立发布门禁。

完成标准：全部关键路径通过；无静默失败；中止和重启不丢项目状态；安装包可在干净环境完成首个任务。

## 5. 发布门禁

- 核心单元、Python、桌面和安装测试通过；
- 至少完成快速检查、简单建模、受控修改和正式发布四个真实任务；
- 无错误项目、错误对话、错误模型或过期批准混用；
- Git 不提交 STEP、图片、缓存、凭据或用户已有暂存内容；
- 首个状态反馈及时，长操作持续显示真实进度；
- Reviewer、人工批准和用户评分在数据与界面中明确分开；
- UI 在目标分辨率、缩放、键盘和减少动画模式下通过检查；
- 发布产物包含安装包、版本说明、已知限制和回退方法。

## 6. 明确不做

- 不建设分布式模型对象库；
- 不把 STEP 提交进 Git；
- 不让通用工具理解自然语言验收要求；
- 不增加大量只能按固定顺序调用的新接口；
- 不自动解决 Git 冲突；
- 不让蒸馏结果未经验证直接覆盖正式规则；
- 不以演示截图替代真实任务测试。
